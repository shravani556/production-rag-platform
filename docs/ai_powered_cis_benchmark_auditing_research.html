1. Current-state baseline

What the PDF already defines

The source PDF describes an automation framework for CIS Benchmark compliance scans across Linux VMs. The existing design uses Jenkins for orchestration, Ansible for remote execution and collection, OpenSCAP on the target VMs for benchmark evaluation, and a centralized HTML dashboard for publishing scan results.

Jenkins Pipeline trigger, scheduling, archive, and dashboard publishing.
Ansible Inventory-driven execution across heterogeneous Linux VMs.
OpenSCAP CIS-oriented scan execution and per-VM HTML report generation.

Baseline flow from the PDF

1TriggerJenkins invokes the compliance pipeline on schedule or on demand.
2AutomateAnsible reads inventory and connects to all Linux VMs.
3ScanOpenSCAP evaluates the selected CIS/SCAP profile on each VM.
4AggregateAnsible collects individual reports and supporting artifacts.
5PublishJenkins archives reports and exposes a consolidated HTML dashboard.

PDF alignment: pages 2-3 define the business problem and proposed automation; pages 4-7 define orchestration, automation, execution, publishing, notifications, and SIEM/dashboard integration; pages 8-11 show the dashboard and OpenSCAP report screens.

2. Target-state design

AI-powered architecture overlay

The recommended approach is not to replace OpenSCAP, Ansible, Jenkins, or GitHub Actions with AI. AI should sit as a governed enrichment and decision-support layer around deterministic scanners. Deterministic engines remain the source of compliance truth; AI accelerates interpretation, prioritization, remediation drafting, exception handling, and executive reporting.

Design principle: AI may recommend, summarize, classify, and generate change proposals. It should not silently modify production systems without policy checks, human approval for high-risk changes, auditable logs, and rollback plans.

AI-enhanced end-to-end flow

1. TriggerJenkins or GitHub Actions starts scan based on schedule, commit, image build, VM provisioning, or manual approval.
2. DiscoverPull asset metadata from CMDB/cloud inventory, owner data, exposure, criticality, OS, tags, and lifecycle state.
3. Select profileAI recommends benchmark/profile and exceptions based on OS, role, workload, policy, and prior decisions.
4. Execute scanAnsible/OpenSCAP or Kubernetes scanners run deterministic checks and produce ARF/XCCDF/HTML/JSON outputs.
5. NormalizeParse results into a common schema covering asset, benchmark, score, rule ID, severity, evidence, and remediation.
6. AI analyzeRAG over benchmarks, internal standards, prior tickets, and runbooks clusters findings and explains root cause.
7. Generate fixAI drafts Ansible tasks, shell remediations, Helm/Kustomize patches, Kyverno/Gatekeeper policies, and rollback steps.
8. Approve/applyTicket, PR, change workflow, and policy gates control remediation execution.
9. Verify/reportRe-scan, compare drift, publish dashboard, send Slack/Teams/email, and push events to SIEM/GRC.

5. CI/CD migration

What changes if Jenkins is replaced by GitHub Actions?

The scanning logic can remain largely the same: Ansible still runs the playbook and OpenSCAP still produces compliance artifacts. The main change is the orchestration substrate: Jenkinsfile, Jenkins agents, credentials, artifact publishing, and notifications become GitHub workflow YAML, self-hosted runners, GitHub Secrets/Environments, Actions artifacts, GitHub Pages or internal static hosting, and GitHub-native summaries.

Example GitHub Actions workflow skeleton

name: CIS VM Compliance Audit

on:
  workflow_dispatch:
    inputs:
      environment:
        description: Target environment inventory folder
        required: true
        default: dev
      profile:
        description: CIS/OpenSCAP profile
        required: true
        default: xccdf_org.ssgproject.content_profile_cis
      remediate:
        description: Generate remediation only; do not auto-apply unless approved
        type: boolean
        default: false
  schedule:
    - cron: "0 3 * * *"

permissions:
  contents: read
  actions: read
  pages: write
  id-token: write

jobs:
  scan:
    runs-on: [self-hosted, linux, cis-runner]
    environment: ${{ inputs.environment || 'scheduled' }}
    steps:
      - uses: actions/checkout@v4

      - name: Validate inventory and dependencies
        run: |
          ansible --version
          oscap --version || true
          test -f inventories/${{ inputs.environment || 'dev' }}/hosts.ini

      - name: Run OpenSCAP via Ansible
        env:
          ANSIBLE_HOST_KEY_CHECKING: "False"
        run: |
          ansible-playbook \
            -i inventories/${{ inputs.environment || 'dev' }}/hosts.ini \
            playbooks/cis_scan.yml \
            -e profile=${{ inputs.profile || 'xccdf_org.ssgproject.content_profile_cis' }}

      - name: Normalize scanner outputs
        if: always()
        run: python tools/normalize_openscap_results.py --input reports/raw --output reports/normalized/findings.json

      - name: AI enrich and summarize findings
        if: always()
        run: python tools/ai_enrich_findings.py --findings reports/normalized/findings.json --out reports/dashboard/index.html

      - name: Upload compliance artifacts
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: cis-compliance-reports
          path: reports/
          retention-days: 30

      - name: Upload GitHub Pages artifact
        if: always()
        uses: actions/upload-pages-artifact@v3
        with:
          path: reports/dashboard

  deploy-pages:
    needs: scan
    if: always()
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
Recommendation: keep remediation generation and remediation application as separate workflows. The first workflow produces PRs/tickets; the second applies approved remediations through protected environments.
6. Kubernetes and container extension

Will this process apply to Kubernetes containers and pods?

Yes, the operating model applies, but the scanner targets and remediation mechanics change. OpenSCAP-on-VM is appropriate for Linux node or VM host compliance. Kubernetes requires cluster-level, node-level, workload-manifest, admission-policy, and container-image controls. Pods are ephemeral, so policy and image checks should happen before deployment and again through in-cluster continuous scanning.

Kubernetes AI-powered flow

1GitOps triggerPR, Helm chart change, cluster schedule, or new image build starts workflow.
2Pre-deploy checksScan image, SBOM, secrets, and Kubernetes manifests.
3Cluster CIS scanRun kube-bench/Trivy against cluster and node configuration.
4AI enrichMap failed controls to owners, namespaces, workloads, root cause, and policy gaps.
5Remediate/preventCreate YAML/Helm/Kustomize patches and Kyverno/Gatekeeper audit or enforcement policies.

Important Kubernetes caveats

  • Managed Kubernetes: EKS, AKS, and GKE often hide control-plane files and flags. Some CIS checks will be not applicable, provider-managed, or require provider-specific benchmark profiles.
  • Pods are ephemeral: avoid scanning every pod like a VM. Prefer image scanning, manifest scanning, admission controls, and Trivy Operator-style continuous in-cluster reporting.
  • Host-level access: kube-bench and node collectors may require privileged access to host namespaces or directories. This must be approved and isolated.
  • Policy lifecycle: start generated policies in audit mode, review false positives, then move to enforce mode with exceptions and expiration dates.
7. Output design

Expected outputs from the AI-powered framework

Operational outputs

  • Consolidated HTML dashboard with global compliance score, per-asset score, top failed rules, severity distribution, and trend line.
  • Per-VM and per-cluster evidence bundles: raw OpenSCAP ARF/XCCDF/XML, HTML, normalized JSON, kube-bench logs, Trivy reports, policy reports.
  • AI-generated executive summary: what changed, why it matters, business risk, SLA, and owners.
  • AI remediation backlog grouped by root cause and owner.
  • ChatOps notifications with top changes and deep links to reports, tickets, and PRs.

Engineering outputs

  • Reviewable remediation PRs for Ansible roles, Packer/Image Builder recipes, Terraform, Helm charts, Kustomize overlays, and policy-as-code.
  • ServiceNow/Jira tickets with generated description, evidence, owner, SLA, exception path, and rollback guidance.
  • Machine-readable JSON/CSV for data lake, SIEM, and GRC ingestion.
  • Audit-ready control mapping to CIS rule IDs and internal policies.
  • Regression reports comparing previous vs current scan outcomes.

AI governance controls

  • Evidence-first: every AI conclusion must cite raw scanner evidence, source benchmark text, or internal policy.
  • Least privilege: AI service has read-only access to findings and approved documents; write operations happen through PRs/tickets.
  • Human approval: require approval for remediation that changes authentication, network, kernel, audit, SELinux/AppArmor, kubelet, API server, or production runtime settings.
  • Prompt/data hygiene: redact secrets, tokens, host private keys, and sensitive business data before LLM calls.
  • Model observability: log prompt template version, model version, sources used, generated output, reviewer feedback, and execution result.
  • Rollback: every generated remediation must include rollback instructions and a re-scan verification step.
9. Implementation appendix

Practical implementation details

OpenSCAP command pattern

oscap xccdf eval \
  --profile "$PROFILE_ID" \
  --results-arf "reports/${HOSTNAME}/results.arf.xml" \
  --report "reports/${HOSTNAME}/report.html" \
  /usr/share/xml/scap/ssg/content/ssg-${OS_ID}-ds.xml

oscap-report -f JSON -o "reports/${HOSTNAME}/result.json" "reports/${HOSTNAME}/results.arf.xml"

AI prompt contract for remediation generation

System role:
  You are a security automation assistant. Use only provided scanner evidence,
  approved runbooks, and benchmark text. Do not invent controls or claim a fix was applied.

Inputs:
  - Failed rule ID, title, severity, benchmark version, scanner evidence
  - OS/distribution or Kubernetes version
  - Existing Ansible role / Helm chart / Kustomize overlay
  - Approved internal remediation patterns

Required output:
  - Root cause hypothesis with confidence
  - Proposed fix as code patch
  - Expected impact and blast radius
  - Rollback steps
  - Verification command
  - Whether human approval is required
