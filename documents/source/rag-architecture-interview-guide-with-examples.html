01

What is RAG?

The foundation concept, in plain language, before any architecture.

Simple explanation

An LLM by itself only knows what it learned during training. Retrieval-Augmented Generation (RAG) is a technique that lets the model look things up in your own documents before it answers — like an open-book exam instead of a closed-book one. The model's job shrinks from "know everything" to "reason well over what was just handed to it."

In one sentence: RAG = search your data → hand the model the relevant pieces → let it write the answer using them.

Why RAG instead of relying only on the LLM?

Problems RAG solves
  • Hallucination — model invents facts when it doesn't know something
  • Staleness — training data has a cutoff date
  • No private data — the model never saw your internal documents
  • No traceability — a raw LLM answer has no citation back to a source
  • Fine-tuning is expensive — retraining for every new document is impractical
What RAG gives you instead
  • Answers grounded in current, verifiable documents
  • Source citations for every answer
  • Easy updates — just re-index a document, no retraining
  • Data stays in your own store, not baked into model weights
  • Lower cost than continuous fine-tuning

Model knowledge vs. external knowledge retrieval

Model (parametric) knowledgeRetrieved (non-parametric) knowledge
Baked into the model's weights during trainingPulled live from an external store at query time
Frozen at the training cutoffAlways as current as the last re-index
Cannot be traced to a sourceComes with document ID, page number, citation
Cannot contain private/internal dataCan contain any document you index — internal or classified
Changing it requires fine-tuning/retrainingChanging it means uploading or removing a document

Common enterprise & government use cases

Enterprise
  • Internal knowledge base / helpdesk copilots
  • Customer support over product manuals
  • Contract & policy Q&A
  • Sales enablement / RFP response drafting
  • Engineering docs and runbook search
Government
  • Citizen services chatbots over regulations
  • Case-file and legal precedent search
  • Policy and compliance research assistants
  • Classified/air-gapped document Q&A
  • Multi-agency records search
Shared drivers
  • Answer must be traceable to a source
  • Data cannot leave a controlled boundary
  • Content changes faster than a model can be retrained
  • Auditability and access control matter as much as accuracy

RAG in real business scenarios

HR policy assistant

User asks: “Can I claim taxi expenses for a client visit?”

RAG action: retrieves the travel reimbursement policy, page 4, section “Taxi Claims.”

Answer: “Yes. Taxi expenses are reimbursable up to AED 150 per approved client trip, with receipts submitted within 30 days.”

Government regulation chatbot

User asks: “What documents are required to renew a trade license?”

RAG action: searches the latest licensing regulation, not the model’s memory.

Answer: lists the exact required forms, fees, validity period, and source regulation.

Engineering runbook copilot

User asks: “What should I do if the payment API returns 502?”

RAG action: retrieves the incident runbook and the recent postmortem.

Answer: gives the escalation path, health-check command, rollback step, and owner team.

Key idea: RAG does not make the model memorize private documents. It retrieves the right private document sections at question time and asks the model to reason over those sections.

03

RAG Pipeline Flow

RAG really runs as two independent pipelines: one that happens once per document (ingestion) and one that happens on every question (query-time).

A. Document ingestion pipeline

flowchart LR A[Upload: PDF, Word, PPT, Excel, CSV, JSON, Images, Scans, HTML] --> B[File Validation] B --> C[Text Extraction] C --> D[OCR where needed] D --> E[Clean and Normalize] E --> F[Chunking] F --> G[Add Metadata] G --> H[Generate Embeddings] H --> I[(Store in Vector DB / Search Index)] B --> J{Duplicate?} J -- Yes --> K[Version and Re-index] J -- No --> C K --> I

Key decision point: duplicate detection happens right after validation — usually via a content hash — so the same file uploaded twice doesn't create duplicate vectors; instead it triggers versioning and selective re-indexing.

B. Query-time pipeline

flowchart LR A[User Question] --> B[Clean / Rewrite Query] B --> C[Generate Query Embedding] C --> D[Vector Search] B --> E[Keyword Search] D --> F[Hybrid Merge] E --> F F --> G[Re-rank Top Candidates] G --> H[Build Prompt: Question + Top Chunks] H --> I[LLM Generates Answer] I --> J[Attach Citations / Sources] J --> K[Return Answer to User] K --> L[Log + Capture Feedback]
Interview framing: "Ingestion happens once per document and is write-heavy; query-time happens on every question and must be low-latency. The two pipelines share the embedding model but almost never share the same infrastructure scaling profile."

04

What Is Indexing?

Indexing is what makes search fast — without it, every query would mean scanning every document from scratch.

Indexing is the process of pre-organizing content into a structure that supports fast lookup at query time, instead of scanning raw documents on every question.

Keyword indexing vs. vector indexing

Keyword IndexingVector Indexing
Matches onExact words / tokensMeaning / semantic similarity
StructureInverted indexVector space (embeddings)
Good atExact terms, IDs, codes, namesParaphrases, concepts, "similar meaning" queries
Weak atSynonyms, paraphrasingExact numbers/codes, rare tokens
Example techElasticsearch, OpenSearch, Lucenepgvector, Milvus, Qdrant, Azure AI Search vector index

What actually gets indexed

  • Text — the chunk content itself
  • Chunks — segmented pieces of the source document
  • Metadata — source file, author, department, sensitivity tag, date
  • Embeddings — the numeric vector for each chunk
  • Document IDs — for grouping chunks back to the parent file
  • Page numbers / section titles — for citations and precise navigation

Re-uploading the same document

  1. The system computes a hash (e.g. SHA-256) of the file content on upload.
  2. If the hash matches an existing document, it's flagged as a duplicate and the upload can be skipped or treated as a new version.
  3. If content changed, the file is assigned a new version number, and only the changed chunks are re-embedded (delta re-indexing) rather than the whole document.
  4. Old vectors tied to the previous version are either kept (versioned history) or retired, depending on business rules.

Keyword, vector, hybrid, and metadata indexing examples

Source chunks to index

Chunk A: Employees can claim taxi reimbursement up to AED 150 per trip for approved client meetings.
Chunk B: Invoice INV-2291 was submitted by Finance on 12 March 2026.
Chunk C: Annual leave entitlement is 30 calendar days after one year of service.

Builds an inverted index from terms to chunks.

Vector indexing

Stores embeddings so the system can search by meaning.

Query vector for “Can I expense a cab?”: [0.11, -0.40, 0.84, ...]

Hybrid indexing

User query: “What is the refund process for order ORD-7781?”

  • Keyword search finds exact order ID ORD-7781.
  • Vector search finds semantically related chunks about refunds, returns, approvals, and payment reversal.
  • Hybrid merge combines both, so the answer is tied to the exact order and the correct refund policy.

What Is Chunking?

Chunking decides how much text becomes one retrievable unit — arguably the single highest-leverage design decision in a RAG system.

Chunking is splitting a document into smaller pieces so that (a) each piece fits the embedding model's input limit, (b) each piece is small enough to be specific, and (c) each piece is still large enough to carry meaning on its own.

Chunking strategies

StrategyHow it splitsBest for
Fixed-sizeEvery N tokens/charactersSimple, uniform text; fast to implement
Sentence-basedAt sentence boundariesPreserving grammatical completeness
Paragraph-basedAt paragraph breaksNarrative or explanatory content
SemanticAt meaning shifts (embedding similarity drop)Long-form content with topic changes
Page-basedOne chunk per pageScanned reports, regulatory filings
Section/header-basedAt heading structure (H1/H2, numbered clauses)Manuals, policies, legal contracts
Table-awareKeeps a full table (or logical row groups) intactFinancial statements, spec sheets
Slide-awareOne chunk per slide (+ speaker notes)PowerPoint decks

Chunk overlap

Overlap means the end of one chunk repeats at the start of the next (typically 10–20% of chunk size). It prevents a fact from being split exactly at a chunk boundary and losing context on either side.

Chunk size depends on

  • Document type — dense legal text needs smaller chunks than narrative text
  • Model context window — bigger windows tolerate more/larger chunks per prompt
  • Embedding model limits — most cap input at 512–8192 tokens
  • Retrieval quality — too large dilutes relevance; too small loses context
  • Answer accuracy — precise answers need precise, well-scoped chunks
  • Latency — smaller chunks retrieve faster but need more of them
  • Cost — more chunks = more tokens = higher LLM cost
  • Domain complexity — technical/legal domains often need smaller, denser chunks

Practical chunk-size starting points

Document typeTypical chunk sizeNotes
PDF (general)500–1000 tokensSection-based when structure exists
Word documents500–800 tokensSplit on headings first
PowerPoint1 slide/chunkInclude speaker notes as extra context
Excel/CSVRow-group or sheet-basedRow + headers together for meaning
JSONPer object/recordFlatten nested keys into readable text
Scanned imagesPer pageDepends heavily on OCR quality
Legal documents200–500 tokensSplit by clause/section number
Technical manuals300–600 tokensKeep procedure steps together
Policy documents300–500 tokensOne policy clause per chunk
Government reports500–800 tokensPreserve section/annex structure

OCR in RAG

OCR is the bridge between "pixels" and "text" — without it, scanned content is invisible to a RAG system.

OCR (Optical Character Recognition) converts images of text — scans, photos, screenshots — into machine-readable text that can be chunked and embedded like any other document.

When OCR is required

  • Scanned PDFs (no text layer)
  • Photographed documents
  • Screenshots
  • Handwritten forms
  • Government/legacy paper forms
  • Faxed documents
  • Tables embedded inside images
  • Charts with labeled data
  • Signed/stamped documents

Where OCR sits in the pipeline

File Processing detects whether a document already has a text layer. If not (or if it's an image format), the file is routed to the OCR engine, which returns extracted text plus, ideally, bounding-box/page-position metadata — before the text ever reaches chunking.

Limitations & downstream effects

Garbage in, garbage out: OCR errors (misread characters, merged columns, missed handwriting) become permanent text errors. Bad OCR text produces bad embeddings, which produces irrelevant retrieval, which produces a wrong or fabricated-sounding answer — the error compounds at every downstream stage.
  • Struggles with poor scan quality, skewed pages, low-contrast text
  • Complex table layouts can lose row/column alignment
  • Handwriting recognition accuracy is far lower than printed text
  • Mitigations: confidence-score thresholds, human-in-the-loop review for low-confidence pages, image pre-processing (deskew, denoise)

Embedding Models

Embeddings are what make "search by meaning" possible instead of just "search by exact word."

An embedding model converts a piece of text into a fixed-length vector of numbers positioned in a high-dimensional space, such that texts with similar meaning land close together in that space. This is what powers semantic search: the system compares vector positions, not literal words.

Embedding model vs. reasoning/LLM model

Embedding modelReasoning / LLM model
Input → OutputText → vector of numbersText → generated text
JobRepresent meaning for comparisonReason, synthesize, and write an answer
Used atIngestion (once) and query time (once per query)Query time, after retrieval
Relative costCheap, fastExpensive, slower

Popular embedding models

Commercial / cloud
  • OpenAI text-embedding-3
  • Azure OpenAI embeddings
  • AWS Titan Embeddings
  • Google Vertex AI embeddings
  • Cohere embed models
Open-source
  • BGE (BAAI General Embedding)
  • E5 (Microsoft)
  • Instructor models
  • Sentence Transformers (all-MiniLM etc.)
Selection criteria
  • Multilingual coverage
  • Vector dimensionality vs. storage cost
  • Self-hostable for data residency
  • Domain fit (legal, medical, code)
  • Latency and throughput

For enterprise or government use, the deciding factors are usually: can it run inside our security boundary, does it support the required languages, and does its accuracy on domain-specific text justify its cost/latency versus a smaller open-source model.

Embedding examples and model choices

Semantic similarity example

Text 1: Employees may claim taxi reimbursement for client meetings.
Text 2: Staff can expense cab rides for customer visits.
Text 3: Passwords must be changed every 90 days.

Text 1 and Text 2 should land close together in vector space because they mean almost the same thing. Text 3 should land far away because it is about cybersecurity, not travel expenses.

08

Vector Search & Vector Databases

How the system actually finds "the closest meaning" among millions of chunks.

Vector search finds the stored vectors that are mathematically closest to a query's vector — the underlying mechanism of semantic search.

Similarity metrics, in plain terms

Cosine similarity

Measures the angle between two vectors — ignores length, focuses purely on direction/meaning. Most common for text embeddings.

Dot product

Combines angle and magnitude. Fast to compute; used when vectors are normalized.

Euclidean distance

Straight-line distance between two points in vector space — smaller distance means more similar.

Approximate Nearest Neighbor (ANN)

Scanning every vector for an exact match doesn't scale past a few thousand items. ANN algorithms (like HNSW or IVF) trade a small amount of accuracy for massive speed gains, making millisecond search possible across millions of vectors.

Vector search vs. keyword search

Keyword searchVector search
StrengthExact terms, codes, namesMeaning, paraphrase, concepts
WeaknessMisses synonymsCan miss exact identifiers
Example query"invoice #INV-2291""how do refunds work"

Hybrid search

Hybrid search runs both keyword and vector search and merges the results (often via a weighted score or reciprocal rank fusion), giving you the precision of keyword matching plus the recall of semantic matching. Most production RAG systems default to hybrid rather than picking one.

When to use which: pure vector search for conceptual/FAQ-style queries; pure keyword search when users search by ID/code/exact term; hybrid as the safe enterprise default, especially for mixed technical + narrative content.

Vector search and hybrid search examples

Cosine similarity example

Query: “Can I expense a cab?”

Candidate chunkSimilarity scoreDecision
Taxi expenses are reimbursable for client meetings.0.91Retrieve

Where vector search is weak

Query: “INV-2291.”

Invoice IDs do not carry semantic meaning. A keyword index is safer for exact identifiers, codes, SKUs, clause numbers, and transaction IDs.

Production hybrid search

Query: “What is the refund status for invoice INV-2291?”

  • Keyword search locks onto INV-2291.
  • Vector search finds chunks about refunds, reversals, approvals, and payment status.
  • Hybrid ranking combines exact ID precision with semantic recall.

ANN example

A system with 40 million chunks cannot compare the query vector against every vector exactly. HNSW or IVF creates a navigable index so the system searches likely neighborhoods first, returning results quickly with a small accuracy tradeoff.

Re-ranking

Retrieval gets you a shortlist fast; re-ranking makes that shortlist actually good.

Initial retrieval (vector/hybrid search) is optimized for speed across a huge index — it returns a broad top-k candidate set (say, top 50). Re-ranking then applies a more expensive, more accurate model to that much smaller set to re-order it by true relevance, and only the top few (top-n) go into the prompt.

Common re-ranking approaches

  • Cross-encoder re-rankers — jointly score query+chunk pairs for high accuracy
  • Cohere Rerank — managed re-ranking API
  • BGE re-ranker — open-source cross-encoder
  • LLM-based re-ranking — ask the LLM itself to score/order chunks
  • Metadata-based scoring — boost by recency, department, document type
  • Hybrid scoring — combine semantic score + metadata boosts
Where re-ranking fits
flowchart LR Q[Query] --> R1[Initial Retrieval: top-k ~ 20-50] R1 --> RR[Re-ranker: cross-encoder / LLM] RR --> R2[Final Set: top-n ~ 3-8] R2 --> P[Prompt Construction]

Choosing top-k vs. top-n: top-k (initial retrieval) is set generously to maximize recall, typically 20–50 candidates. top-n (post-rerank) is kept small, typically 3–8, to fit the context window, control cost, and avoid diluting the LLM's attention with marginal chunks.

Re-ranking example

User question: “Can I claim taxi expenses for a client visit?”

Reasoning Model / LLM

The component that turns retrieved facts into a coherent, well-written answer.

The reasoning model (LLM) takes the constructed prompt — instructions, the user's question, and the top retrieved chunks — and generates the final natural-language answer, ideally staying grounded in the provided context rather than its own memorized knowledge.

Model typeJob

  • Llama models (Meta)

Model selection criteria

  • Accuracy
  • Reasoning ability
  • Context window size
  • Cost per token
  • Latency
  • GPU requirements (self-hosted)
  • Data privacy / compliance
  • Multilingual support
  • Fine-tuning support

For government and highly regulated sectors, data privacy and compliance usually override raw accuracy — which is why self-hosted open-weight models (Llama, Mistral, Qwen) on GPU clusters inside a controlled boundary are common, even if a managed API model would score higher on benchmarks.

RabbitMQ & Messaging

Ingestion is bursty and slow (OCR, chunking, embedding); messaging decouples that from the fast, interactive parts of the system.

RabbitMQ is an open-source message broker that lets services communicate asynchronously by publishing and consuming messages through queues, instead of calling each other directly and waiting.

Why queues in RAG ingestion

  • Document processing (OCR, chunking, embedding) is slow and variable in duration — you don't want the upload API to block on it
  • Large batch uploads create bursts of work that need to be smoothed out over time (buffering)
  • If a processing worker crashes mid-document, the message can be retried instead of losing the job
  • Different stages (OCR → chunk → embed) can scale independently as separate consumers
RabbitMQ in the ingestion pipeline
flowchart LR API[Upload API] -- publish --> Q1[[Queue: raw-documents]] Q1 --> W1[OCR Worker] W1 -- publish --> Q2[[Queue: parsed-text]] Q2 --> W2[Chunking Worker] W2 -- publish --> Q3[[Queue: chunks]] Q3 --> W3[Embedding Worker] W3 --> VDB[(Vector DB)]

Interview Preparation

Click each question to reveal a tight, interview-ready answer. Practice saying these out loud in under 30 seconds each.

What is RAG?

RAG is an architecture that grounds an LLM's answers in external documents by retrieving relevant content at query time and injecting it into the prompt — instead of relying only on what the model memorized during training.

Why do we need RAG?

To reduce hallucination, keep answers current without retraining, ground responses in private/internal data the model never saw, and provide traceable citations — all at a fraction of the cost of fine-tuning.

What is indexing?

Indexing is pre-organizing content — text, chunks, metadata, embeddings — into a structure optimized for fast lookup, so queries don't require scanning every document.

Why do we need indexing?

Without an index, every query would require a full scan of all documents, which doesn't scale past a small collection. Indexing trades storage and pre-processing time for near-instant retrieval.

What is chunking?

Splitting a document into smaller, retrievable pieces so each unit is small enough to be specific and fits model/embedding input limits, but large enough to still carry standalone meaning.

How do you decide chunk size?

Balance document type, embedding/context window limits, retrieval precision, answer accuracy, latency, and cost. Start around 300–800 tokens with 10–20% overlap, then tune based on retrieval evaluation results for the specific domain.

What is OCR?

Optical Character Recognition — converts images of text (scans, photos, screenshots) into machine-readable text so it can be chunked and embedded like any other document.

Why is OCR needed in RAG?

Because a large share of enterprise/government content exists as scans or images with no underlying text layer; without OCR that content is completely invisible to the retrieval system.

What is an embedding model?

A model that converts text into a numeric vector positioned so that texts with similar meaning are close together in vector space — the mechanism behind semantic search.

Why do we need embeddings?

They let the system match queries to content by meaning rather than exact words, so paraphrased or conceptually related questions still retrieve the right chunks.

What is vector search?

Finding the stored vectors mathematically closest to a query vector — typically using cosine similarity — often accelerated with approximate nearest neighbor algorithms for scale.

Why do we need vector search?

Keyword search alone misses synonyms and paraphrasing. Vector search retrieves by meaning, which is essential for natural-language questions over large document sets.

What is re-ranking?

A second, more accurate scoring pass over the initial retrieval candidates, applied because fast retrieval methods trade some accuracy for speed at scale.

How does re-ranking work?

Retrieval returns a broad top-k candidate set; a cross-encoder or LLM-based re-ranker scores each candidate more precisely against the query; only the top-n survivors go into the final prompt.

What is a reasoning model?

The LLM component that takes the assembled prompt — instructions plus retrieved context — and generates the final coherent, grounded answer.

Why do we need a reasoning model?

Retrieval only finds relevant raw text; it doesn't synthesize, compare, or explain. The reasoning model turns retrieved facts into a coherent, natural-language answer to the user's actual question.

What is RabbitMQ?

An open-source message broker that enables asynchronous communication between services via queues, commonly used to decouple slow document-processing stages from the fast upload API.

Why do we need queues in RAG?

Ingestion steps like OCR, chunking, and embedding are slow and bursty. Queues buffer that work, allow independent scaling per stage, and support retries if a worker fails.

What happens when the same document is uploaded again?

A content hash is computed and compared to existing records. If unchanged, it's treated as a duplicate and skipped. If changed, it's versioned and only the affected chunks are re-embedded and re-indexed.

How do you design a RAG pipeline?

Separate ingestion (parse → OCR → clean → chunk → embed → index) from query-time (rewrite → retrieve → re-rank → prompt → generate → cite). Design each layer for its own scaling and latency profile, add metadata for access control, and instrument logging/feedback throughout.

How does RAG architecture differ between on-premises and cloud?

On-premises trades convenience for full data control — self-hosted OCR, vector DB, and LLM on owned GPUs, with more operational overhead. Cloud swaps those for managed equivalents (Document Intelligence/Textract, Azure AI Search/Bedrock/Vertex, managed LLMs), reducing ops burden but introducing data-residency and vendor considerations.

How would you design RAG for government or highly secure environments?

Keep everything inside a controlled network boundary: self-hosted or sovereign-cloud OCR, embedding, vector DB, and open-weight LLM on GPUs; strict RBAC and document-level access control tied through metadata; full audit logging; encryption at rest and in transit; and no data egress to public model APIs.

Interview scenario examples

Scenario 1: The interviewer asks how you handle scanned PDFs

Answer: “First I detect whether the PDF has a text layer. If it does, I parse text directly. If it does not, I route pages to OCR, store OCR confidence and page metadata, then clean, chunk, embed, and index. Low-confidence pages go to review so bad OCR does not poison embeddings.”

Scenario 2: The interviewer asks keyword vs vector search

Answer: “Keyword search is best for exact identifiers like invoice numbers, policy IDs, product codes, and clause numbers. Vector search is best for paraphrased natural-language questions. In production I usually use hybrid search, then re-rank the merged candidates.”

Scenario 3: The interviewer asks about secure government RAG

Answer: “I would keep OCR, embeddings, vector DB, metadata store, and LLM inference inside the controlled boundary. I would enforce document-level access control through metadata filters at retrieval time, add audit logs, encrypt data at rest and transit, and avoid public model APIs unless approved by policy.”

Best Practices

Chunk size selection

Start with domain-appropriate defaults (Section 5), then tune using retrieval evaluation — not intuition alone.

Metadata design

Capture source, owner, sensitivity tag, date, and section/page upfront; retrofitting metadata later is expensive.

Hybrid search

Default to hybrid (vector + keyword) unless you have strong evidence one alone suffices for your query patterns.

Re-ranking

Always re-rank when top-k retrieval exceeds ~10 candidates; skip it only for very small, low-stakes indexes.

OCR quality control

Track OCR confidence scores; route low-confidence pages to human review rather than silently indexing bad text.

Document versioning

Never overwrite embeddings in place; version documents so answers can be traced to the exact version in effect at query time.

Duplicate detection

Hash content on upload (not just filename) to catch true duplicates and avoid redundant storage/embedding cost.

Access control

Enforce permissions at retrieval time using metadata filters, not just at the UI layer — never let a query return chunks the user isn't authorized to see.

Secure / private RAG

Keep embeddings and LLM inference inside your security boundary for sensitive data; avoid sending regulated content to public APIs without a data processing agreement.

Cost optimization

Cache frequent query embeddings, right-size top-k/top-n, and use smaller embedding models where domain accuracy allows.

Latency optimization

Use ANN indexes, keep re-ranking sets small, and consider streaming the LLM's response back to the user.

Evaluation and testing

Continuously measure retrieval precision/recall and answer faithfulness against a labeled test set — RAG quality drifts as documents and query patterns evolve.

Best-practice examples and anti-patterns

Bad: UI-only security

The UI hides confidential documents, but retrieval can still return confidential chunks if the user asks the right question.

Good: retrieval-time security

Every vector search includes metadata filters such as tenant_id, department, classification, and allowed_roles.

Bad: overwrite vectors in place

Old answers cannot be traced because document versions are lost.

Good: version every document

Store document_id, version, chunk_id, page, and indexed_at with every chunk.

Bad: index low-quality OCR blindly

Misread invoice numbers and names pollute the index.

Good: OCR confidence thresholds

Pages below the confidence threshold are reviewed or reprocessed with deskew/denoise before indexing.
